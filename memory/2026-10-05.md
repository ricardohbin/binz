# 2026-10-05

## Session 1 — tuples, `Tuple<A, B>(a, b)`, Error-first

On `main`, clean at `c443078 feat: adding LSP support (#13)`. Left uncommitted.

### His ask

"let's support tuples! with it, we can have multiple return values. remember
our error handling strategy: ALWAYS an error must be the first element of a
return tuple that contains error. we can infere it in compile time. No
shorthand to tuple, let's use Tuple<Type, type, type>(value, value, value)"

### What shipped

- `Tuple<A, B, ...>` type, `Tuple<A, B>(a, b)` literal. `Tuple` is a lexer
  keyword (`Tok::Tuple`), like `Vector`/`HashMap`.
- `Type::Tuple(Vec<Type>)`: an aggregate, flat layout, copied by value —
  a struct with unnamed fields. So returns ride the existing sret path,
  params copy, `var`/`const` work. **No VM, opcode or artifact change.**
- **Element access is `t[0]` — my call, not his.** `[]` is already "the one
  way to reach an element", so no `t.0`. The index must be an integer
  literal (each element has its own type). `t[1] = x` on a `var` tuple.
- **Error-first rule** in `check_tuple`, run from `resolve_type`, so it holds
  wherever a tuple type is written (return, param, var, field, fn type):
  `Error` at index > 0 is refused, naming the reordered type; a second
  `Error` is refused ("carries one `Error`"). Only direct elements —
  `Tuple<i32, [Error; 2]>` passes.
- Also refused: `Tuple<T>` (is just `T`), `void` elements, the `(a, b)`
  shorthand (parser diagnostic), `Tuple<..>{}`, arity mismatch.
- `T{}` recurses into tuple fields; `json_holds` refuses tuples; `struct_in`
  recurses, so `Tuple<Error, P>` with a module-private `P` can't cross.
- Editor: `tuple_type`/`tuple_keyword`/`tuple_literal` in `grammar.js`,
  regenerated `src/`; highlights; `complete.rs` GENERICS + angle rule.
  **`rev` in `editors/zed/extension.toml` not bumped** — it must point at a
  pushed commit containing the grammar, which only he can make.
- README "Tuples" section + one-way table row. `examples/tuples.binz`
  (main + 2 tests).

### Tests — 142 -> 148 e2e (+30 unit), all green; both CI example loops pass.

### Flagged, not decided by him

- `t[0]` vs `t.0` (above).
- **No destructuring** (`const (err, n) = f();`): it would be a second way to
  read an element. Reading is `r[0].code` / `r[1]`.
- **`binz/json` still uses the out-pointer** (`json.parse(text, &p): Error`),
  which existed only because there were no tuples. Now two conventions for
  "error + value" coexist — a one-way-rule violation. `json.stringify(p)`
  could become `Tuple<Error, str>` trivially; `json.parse` needs the target
  type, i.e. a new `json.parse<Point>(text)` form. His call.
- Error-first is enforced for **every** tuple, not only return tuples.
- A function may still return a bare `Error` (no value) — kept.
