# 2026-09-14

## Session 1 — HashMap<K, V>

He asked for it plainly: "we need to implement HashMap in binz. it's a
classic, we need it, right?" Branch was already `feat/struct-in-containers`,
sitting exactly on `main` (fb05c95, the containers PR) with a clean tree — so
the branch name is about something else he has not started. I built HashMap
on it anyway; the tree is uncommitted, as always.

### The design, and the one-way argument for each piece

- **`HashMap<K, V>`** — the first and only type with two arguments. That is
  why it is *not* a `Kind`: `Kind` carries the sequence/set dichotomy
  (`is_sequence` is literally `!is_set`), so folding a map into it would have
  made every map silently a "sequence". New `Type::Map`, `TypeExpr::Map`,
  `Tok::Map`, `Expr::MapLit` instead. Cost: ~7 extra match arms. Worth it.
- **`m[key] = value` is the only way to insert.** It inserts when the key is
  new and overwrites when it is not, so there is no `add`/`insert`/`put`
  triplet to choose from. `add`, `push` and `insert` on a map all error with
  "write `m[key] = value`".
- **Reading a missing key traps.** No `null`, no optional, so no third state
  to design. `contains(m, k)` is the guard, and the trap message says so.
- **`keys(m)` returns `Vector<K>`**, insertion order, and there is
  deliberately **no `values`** — `m[k]` already answers that, and a second
  spelling for the same walk is exactly what the rule forbids.
- **`remove` takes a key**, so a map gets `remove`, never `erase`. Same split
  as the sets. `find` errors and points at `contains`.
- Literal `HashMap<str, i32>{"a": 1, "b": 2}`. The `:` is unambiguous: struct
  literals want an *identifier* before `:`, a map literal wants an
  expression. Duplicate keys: last wins, one entry — the same shape as
  `Set<i32>{3, 1, 3}` keeping two.
- Key types are the `is_key()` five (`i32 i64 f64 bool str`), values are any
  one-slot type. NaN as a key traps, as with the sets.

### Implementation

`MapData` in `src/obj.rs` is a deliberate twin of `SetData`: `Vec<(Value,
Value)>` plus a `HashMap<Key, usize>`, so insertion order is stable and
`keys` is deterministic across runs. `OP_GET`/`OP_SET` are reused rather than
duplicated — the VM checks `obj::is_map(&h)` and reads the stack value as a
position or as a key. `OP_NEW` gets `KIND_MAP = 4` and takes two stack values
per entry, so its count is twice the length. One new builtin, `B_KEYS = 11`.

42 tests green (6 new), `examples/containers.binz` grew a HashMap section,
README updated throughout.

### Flagged to him, undecided

`Set` is a hash set spelled `Set`, so `HashMap` next to it is asymmetric.
Either the map becomes `Map`, or `Set` becomes `HashSet` — one line in the
lexer plus docs either way. I used his word, `HashMap`. His call.

## Session 2 — the standard library: `import binz/<module>`

He opened with the complaint, not a spec: "all this functions in
containers.binz need to be in standard lib of binz instead of manual
implementation", then proposed the shape himself — `binz/string`, `binz/int`,
`binz/float`, `binz/container`, `binz/io` — and "print can use binz/io".
He corrected two spellings along the way; both have their own section below.

### The design, and the one-way argument for each piece

- **`import binz/io;` binds `io`, and a member is always `io.print`.** The
  binding is the last path segment, always — no `as`, no wildcard, no bare
  import, no `from ... import ...`. That is the whole reason to prefer
  mandatory qualification: two modules can both define `find` and neither has
  to win, so there is never a resolution rule to learn.
- **This retires the shadowing inconsistency I flagged 2026-09-11.** Builtins
  used to resolve last so a user `function add(...)` could shadow the set
  verb, while `print` could not be redefined at all. Now module members live
  in a different namespace entirely: `container.add` never takes the word
  `add` away from the program, and nothing resolves "last". One rule, both
  cases.
- **An import owns its binding program-wide.** Once `binz/io` is in, nothing
  else may be named `io` — struct, function, local or param. One line
  (`check_free`) and it means `io.print` never has to be disambiguated
  against a local named `io`. Chose `.` over `::` because `::` buys only that
  disambiguation, which this rule already gives for free.
- **Imports go first, all of them, before the first item.** The head of a
  file always states its dependencies.
- **`size` is per type family, not universal.** `container.size(c)` and
  `string.size(s)`; `container.size("abc")` is an error that names
  `string.size`. This *looks* like two ways to do one thing and is the
  opposite: a `str` is not a container, and one name meaning one thing per
  type beats one name resolving two ways. Same for `find` and `contains`.
- **`int.parse` answers `i64` and traps; `int.canParse` is the guard.** No
  `null`, so no optional to design — the same shape as `container.contains`
  in front of a `HashMap` read. Narrowing is `cast<i32>`, because `cast` is
  already the one converter. I considered making `parse` hint-driven over
  i32/i64 and dropped it: `canParse` has no hint to read, so the guard and
  the parse would have disagreed about range.
- **`cast<str>` stays the only formatter.** `binz/string` deliberately has no
  `from_int`.
- Every `string` position is a **character** index, matching the existing
  char-counting `len`. `string.at` returns a 1-char `str` since there is no
  char type. `slice` is half-open.

### The rule that settled which members are values

**A stdlib function is a first-class value exactly when its type can be
written down in binZ.** `io.print` is `function(str): void` — writable, so it
is a value. `container.size` answers for six types and `int.max` for two, and
binZ has no user generics, so they have no type to hold and must be called.
This is the principled version of the `print` vs `len` split I called an
inconsistency on 2026-09-11 — it was the right split, it just had no stated
rule. Two tables in `src/stdlib.rs`: `NATIVES` (monomorphic, pushed as a
function value, run by `Vm::call_native`) and `FORMS` (generic, resolved
against the first argument's type, emit `OP_BUILTIN`).

### Implementation

New `src/stdlib.rs` is the whole module table — 28 natives, 15 forms. A
native's **index is its bytecode operand and its arm in `call_native`**, so
`native_indices_are_frozen` pins the order as append-only; that test exists
because nothing else would catch a silent shift. Artifact `VERSION` 1 → 2.
`B_LEN` → `B_SIZE`, plus `B_INT_ABS/MIN/MAX`. `compile_builtin` became
`compile_form(module, member, ...)` and its messages are qualified.
`compile_call` extracted `finish_call` so a native call reuses the ordinary
call path. Imports are step 0 of `Compiler::run`, before struct names.

Every diagnostic carries the line the program should have written, including
a rename table (`RENAMED`) so bare `len(v)` says "`len` is now `size`, in
`binz/string` or `binz/container`; write ... after `import ...`".

59 tests green (16 new) plus 2 unit tests. New `examples/stdlib.binz`;
`containers.binz`, `tour.binz`, `hello.binz` and the README all migrated.
Tests get a `PRELUDE` of all five imports so they only say what they are
about, with `run_raw_ok`/`run_raw_err` for the import rules themselves.

One real bug found on the way: I named a temp file `intfloat`, which an
existing test already used, and the two raced in parallel. Fixed, and
`write_temp` now says why the name must be unique.

## Session 3 — `binz/map` and `SortedMap<K, V>`

"ok, let's create a module called map in stdlib. they will handle all
operations related to our hashmap and future maps. let's do this and create a
new data structure: SortedMap. you can use red black tree in these one."

Tree was clean on `main` at `f6538bf feat: stdlib and imports (#4)` — he did
commit `src/stdlib.rs` and `examples/stdlib.binz` in the end, so the gap I
flagged in session 2 is closed.

### The design, and the one-way argument for each piece

- **A map is a third type family, not a container.** The precedent was
  already set in session 2: `size`/`find`/`contains` are per family, so a
  `str` answers `binz/string` and a container answers `binz/container`. His
  request makes the map the third: `map.size(m)`, and `container.size(m)` is
  now an error naming `map.size`. Six members, and only six: `size`
  `contains` `remove` `keys` `clear` `copy`. `container.keys` is gone.
- **The form ids are shared, the modules are not.** `map.size` and
  `container.size` are both `B_SIZE` — the opcode is what the machine does,
  the module is which family the name belongs to. So no new opcodes at all
  for the module split, only a new `KIND_SORTED_MAP = 5`.
- **A refused verb names the line that works.** New `MISUSED` table in
  `stdlib.rs`: `map.find` -> "use `map.contains`", `map.add` -> "write
  `m[key] = value`", `map.values` -> "read `m[key]` while walking
  `map.keys(m)`", `container.keys` -> "only a map has keys". Without it
  `map.find` would have been answered by pointing at `binz/container`, which
  refuses a map too — a diagnostic that sends you somewhere useless. A test
  (`refused_verbs_are_not_also_defined`) keeps the table and the real members
  from contradicting each other.
- **`SortedMap<K, V>` differs from `HashMap<K, V>` in exactly one thing:**
  the order `map.keys` answers. Same literal shape, same `m[key] = value`,
  same six verbs, same trap on an absent key. That is the whole reason it is
  allowed to exist next to `HashMap` — it is not a second way to do one
  thing, it is the ordered answer to a different question, the way
  `SortedSet` sits next to `Set`.
- **`MapKind` instead of a second `Type` variant.** `Type::Map(MapKind, K, V)`
  mirrors `Type::Container(Kind, T)`. Maps stay their own variant, since
  `Kind`'s dichotomy is still sequence-vs-set.
- **No `first`/`last`/range on the sorted map.** `map.keys(sm)[0]` already
  answers, and inventing spellings he did not ask for is how a library grows
  two ways to do one thing. Flagged below instead.

### Implementation

`SortedMapData` in `src/obj.rs` is a real CLRS red-black tree over a node
arena with a free list, same shape as `List`. `NIL` is `-1` rather than a
sentinel node, so every place CLRS reads `nil.parent` carries the parent
explicitly — `remove_fixup(x, x_parent)` is the one that matters. Deletion
uses the pointer form: the successor takes the removed node's links and
colour, so no key or value ever moves between nodes.

A red-black tree is the one thing here that cannot be trusted by reading it,
so the unit tests assert the invariants directly: root black, no red-red
edge, uniform black height, parent links agree, in-order ascending, `len`
matches — checked **after every step** of 3000 deterministic randomised
inserts and deletes, against a `Vec` oracle. Plus ascending insertion (the
worst case for an unbalanced BST) and arena reuse after churn.

Artifact `VERSION` 2 -> 3, because `KIND_SORTED_MAP` widens `OP_NEW`'s
operand domain and the check is an equality.

Small refactor on the way: `stdlib::join_or` now builds "a, b or c" for both
`describe_modules` and the `len` -> `size` rename hint, which had been
emitting "a or b or c".

73 tests green (66 end to end, 7 unit). `examples/containers.binz` grew a
`SortedMap` section and a `### Maps` section landed in the README.

### Correction, same day: the naming model is Redis, not Java

He pushed back on the flag above: "the concept I am using to Set/SortedSet is
likely one used in redis, forget about java Set Interface."

So I had the analogy wrong in both sessions. I had been reading `Set` as "the
hash implementation of an abstract Set interface", which is the Java frame,
and that is what made `Set` look like an under-specified `HashSet`. Under the
Redis frame there is no interface: a set is just a set (Redis SET), and a
sorted set is the ordered variant (Redis ZSET). **The bare word is the
default, a qualifier marks the variant.**

I then over-corrected: I proposed `HashMap` -> `Map`, on the grounds that
`HashMap` was the only type named for its implementation. He shut that down
too — "redis has Hashes (that are HashMaps) right. keep this way." And he is
right: Redis's map type **is** called a Hash (HSET/HGET), so `HashMap` tracks
the Redis names exactly as `Set` and `SortedSet` do.

So the whole naming scheme comes from one place, Redis's data types:

    SET   -> Set          ZSET -> SortedSet
    HASH  -> HashMap      (no Redis equivalent) -> SortedMap

**The `Set`-vs-`HashMap` asymmetry I flagged in session 1 and re-flagged in
session 3 never existed.** It was an artifact of reading the names through
Java's collections instead of Redis's. Closed, in both directions — no
`HashSet`, no `Map`. No code changed.

The lesson worth keeping: I flagged that "asymmetry" twice across two
sessions without ever asking where the names came from. When a naming call of
his looks inconsistent, the first question is which system he is borrowing
from, not which rename would fix it.

### He asked how `HashMap` actually keys, and it found a doc bug

"our actual HashMap are using hashing to create the keys, right?"

Answered precisely, because the honest answer is "not where you'd think":
`key_of` is **canonicalization, not hashing** — it normalizes a `Value` into
a `Key` (NaN rejected, `-0.0`/`0.0` folded). The hashing is Rust's
`std::collections::HashMap` over the derived `Hash` on `Key`, with the
default `RandomState` (SipHash-1-3, randomly seeded per process). That random
seed is precisely *why* `MapData` keeps its own insertion-ordered `Vec` and
lets the std map hold only indices — iterating the std map directly would
make `map.keys` differ between runs.

Checking it turned up a claim I had written in the README earlier the same
session: the maps table said `HashMap` is "`O(1)` amortised". **It is not for
`remove`** — `entries.remove(pos)` shifts the vector and then reindexes every
slot above `pos`, so removal is `O(n)`. Corrected the table, and added the
consequence: on a delete-heavy workload `SortedMap` is currently the *faster*
map despite the `O(log n)`.

`SetData::remove` has the identical shape and the same `O(n)`, inherited from
2026-09-11 — not something this session introduced. Both would be fixed the
same way (tombstones, or a swap-remove plus an order side-table), and neither
is worth doing until he says the cost matters.

Second `str` cost, untouched: `Key::Str((**x).clone())` allocates a fresh
`String` on every str-keyed lookup, including reads that miss.

Lesson repeated from the naming correction: I wrote a complexity claim into
docs from the shape of the design rather than from the code. Read the
function before writing its cost down.
