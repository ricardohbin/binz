### The shape of the design

Two storage models, and every other rule falls out of which one a type uses:

- `[T; N]` lives in the frame, flat, and **copies** — a value like a struct.
  Any element type, including structs and nested arrays. `&a[i]` is real.
- `Vector<T>` / `LinkedList<T>` / `Set<T>` / `SortedSet<T>` live on the heap
  and are one slot holding an `Rc<RefCell<Obj>>`, so they **alias** on
  assignment. Elements must be one-slot values; sets additionally need a key
  type (`i32 i64 f64 bool str`).

Consequences I decided and wrote down in the README: `const` freezes the
handle and not the contents; `copy(c)` is the one way to get independent
storage and it is deep; a container in a struct field is shared when the
struct is copied; `[Vector<i32>{}; 2]` repeats one handle.

### Syntax

- `[a, b, c]` and `[x; N]`. The literal needs a declared type to know `T` and
  `N`, and must list *every* element — same rule as struct literals.
- `Vector<i32>{}`, `Vector<i32>{1, 2}` — reuses the `Name{...}` literal shape.
  The four names are lexer keywords, so `Vector<i32>` never collides with `<`.
- `c[i]` on all five. Assignable on the three sequences; on a set it errors
  and points at `add`/`remove`. Index is always `i32`.
- Iteration is a `while` over `len`. Both sets have deterministic order
  (Set = insertion, SortedSet = ascending) precisely so this is usable.

### The verbs, and why each container gets exactly one

`len` `find` `push` `pop` `insert` `erase` `add` `remove` `contains` `clear`
`copy`. Split so no container ever has two ways: **`erase` takes a position,
`remove` takes a key**; sequences get `find`, sets get `contains`. Applying
the wrong one is an error that names the right one ("use `add`").

### Two calls worth remembering

1. **Builtins resolve last.** I first made the 11 names reserved; that broke
   `functions_are_first_class`, which defines `function add(...)`, and `add`
   / `find` / `insert` / `remove` are ordinary words a program wants. So a
   user function or local with that name now shadows the builtin. `print` is
   still non-redefinable, so there is an inconsistency there he may dislike.
2. **`[x; N]` alongside `[a, b, c]`.** Two literal forms that overlap for
   `[0; 3]` vs `[0, 0, 0]` — a real bend of the one-way rule, taken because
   enumerating 64 zeros is untenable. Flagged to him; his call to remove.

Builtins are generic over the element type, which binZ cannot write in a
signature, so unlike `print` they are not first-class values. Diagnostic says
so and suggests shadowing.

### Implementation notes

- New `src/obj.rs` holds the heap containers. `LinkedList` is a genuine
  doubly linked list over a node arena with a free list, and `l[i]` walks from
  the closer end — I did not fake it with a `VecDeque`. `Set` is a
  `HashMap<Key, usize>` over an insertion-ordered `Vec`. `SortedSet` is a
  sorted `Vec` with bisection.
- `Type::is_struct` became `Type::is_aggregate` (Struct | Array) everywhere
  the compiler meant "multi-slot, represented by its address". The existing
  sret machinery then handled returning `[T; N]` with no extra work.
- New opcodes: `elem`, `arr.find`, `new`, `get`, `set`, `builtin`.
- `[x; N]` emits a runtime fan-out loop, so the value is evaluated once and a
  long array costs the same code as a short one.
- Assigning `c[i]` compiles the base into a scratch buffer first to learn
  whether it is an array (a place, has an address) or a handle (needs `set`).
- NaN as a set key traps. An empty `SortedSet` never reaches a comparison, so
  the guard had to go at the top of the binary search, not inside it.
- `MAX_SLOTS = 4_000_000` caps what a `[T; N]` annotation can ask of a frame.
