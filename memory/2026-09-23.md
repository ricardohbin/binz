## Session 1 — `binz/json`, `@json`, `@field`, and `Error`

Branch `feat/json-support`, clean at `a6e9253 feat: block scoped variables (#10)`.

### His ask

A JSON module. Map fields as is, rename with an annotation:

    @json
    struct Point {
      @field("some_field")
      someField: string,
      year: i64
    }

`year` needs no mapping; "fields that are not mapped are omitted
automatically". `json.parse` / `json.stringify`. Error handling "always the
first return", as in `var err = json.parse(somepayload); if (err)...`, with

    struct Error { reason: str, stacktrace: str, code: int }

### Where his sketch collided with settled rules, and what I did

- `string` / `int` are not binZ types. Wrote `str`, and `code: i32` (the
  default integer; literals are `i32`).
- `var err = ...` has no type, and binZ has no inference: `var err: Error = ...`.
- **`if (err)` breaks "conditions must be `bool`, no truthiness".** Kept the
  rule; the check is `if (err.code != 0)`, and `if (err)` is refused with a
  diagnostic naming that line (`expect_cond`, also used by `while`). **His
  call to reopen** if he wants it.
- "the first return": binZ has no tuples/multiple returns, so the Error *is*
  the return value and the payload goes through a pointer:
  `json.parse(text, &p): Error`, `json.stringify(p, &text): Error`.
  Stringify can genuinely fail (NaN/inf), so both answer `Error`.
- "not mapped are omitted": read as **unknown JSON keys are skipped on
  parse**. A struct field missing from the JSON is error code 3 — no `null`,
  so there is nothing to leave in it.

### Design

- `Error` is **struct id 0 in every program**, pre-registered in every file's
  `struct_ids`; declaring your own `Error` is refused. It is the **first type
  that crosses a module boundary** (`struct_in` exempts it), so user modules
  can answer `Error` too. Layout fixed: reason 0, stacktrace 1, code 2.
- Success: `code 0`, both strings `""`. Codes: 1 syntax (line/col), 2 type
  (incl. `1.5` into an int, overflow, `null`), 3 missing key, 4 duplicate key,
  5 NaN/inf on stringify. No constants for them — binZ has no enums/consts.
- `stacktrace` is `at f\nat main`, innermost first, **function names only** —
  the artifact has no line table.
- **Destination untouched on failure**: text -> tree -> slots buffer -> copy.
- `@field` refused outside `@json`, refused when it repeats the field name
  (a second spelling of the default), and two fields can't share a key.
- `@json` field types: bool/i32/i64/f64/str/`@json` struct/`[T; N]` (exact
  length)/`Vector<T>`. Checked at the struct declaration, not the call.
- stringify: compact, declaration order, no pretty-print (one spelling).
- Strict RFC 8259 reader (no `01`, `+1`, `.5`, trailing commas, lone
  surrogates), depth cap 512. Numbers kept as lexemes, so i64 is exact.

### Mechanics

- `json.parse`/`stringify` are **forms** (B_JSON_PARSE 17, B_JSON_STRINGIFY
  18). The call reserves an `Error` temp, pushes its address first, and
  pushes the **schema index as an i32 last** — so no new opcode.
- Artifact **VERSION 4 -> 5**: a schema table (`Schema`/`JField`/`JType` in
  `bytecode.rs`), built lazily per struct reached by a json call.
- Runtime in new `src/json.rs`; VM glue is `write_error` + `stacktrace`.
- `rejects_an_unknown_module` used `binz/json` as its missing module; now
  `binz/xml`.

### Tests — 125+12 -> 139 e2e + 12 unit, all green

17 new e2e cases in `tests/lang.rs` (json section at the end), 5 unit tests
in `src/json.rs`. New `examples/json.binz` (main + two `@test`s); both CI
example loops pass by hand. Artifact build/exec/dump round-trips.

### Flagged, not decided by him

- `if (err)` truthiness (above).
- `json.parse` needs an initialised `var` to fill, since binZ has no
  uninitialised declarations — so a caller writes a full struct literal (or a
  `blank()` helper) first. Verbose for big structs.
- No `HashMap<str, V>` <-> JSON object, no optional fields.
- A program can build its own `Error{...}`, and nothing fills `stacktrace`
  for it.
- `Error` taking a name program-wide is the same kind of bite as `map`.

## Session 1, part 2 — `T{}` default literals

His ask: `var p: Point = Point{ someField: "", year: 0 };` is redundant before
`json.parse`; write `Point{}` with defaults `""`, `0`, `0.0`, and bool `false`.

- **All or nothing**: `T{}` or every field in order. Partial literals stay
  refused (the error now mentions `T{}`), else one value gets many spellings.
  This is an overlap with the full literal of all-zero values — same kind of
  bend as `[0; 3]` vs `[0, 0, 0]`, flagged.
- Applies to **every struct**, not just `@json`. Defaults recurse into nested
  structs and each array element; containers/maps default to a fresh empty
  one **per element** (runtime loop, so no shared handle, and code size is
  one element's). A pointer or function field has no default (no `null`):
  the error names the path, e.g. `` `n[i].next` is a `*N` ``.
- `Error{}` is "no error" for free.
- Compile-time only (`compile_default_lit` / `defaultable` / `emit_default`);
  no VM or artifact change. The `blank()` flag from part 1 is closed.
- Tests 139 -> 142 e2e. JSON tests, `examples/json.binz` and README now use
  `T{}`.
