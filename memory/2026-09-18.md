# 2026-09-18

## Session 1 — why CI broke, and the "Run the examples" fix

He opened with "my ci is broken, why". Branch `fix/ci`, clean, identical to
`main` at `6d98a7b feat: test and random modules (#8)`.

### The break

CI's last step ran every `examples/*.binz` as a program:

    for f in examples/*.binz; do cargo run -- run "$f"; done

`#8` added `examples/orders.binz`, which **has no `main` by design** — that is
the whole point of the file, and of `binz test` needing no entry point. So:

    error: every program needs `function main(): i32`
      --> examples/orders.binz:1:1

Exit 1, and GitHub runs `run:` blocks under `bash -e`, so the loop aborted.
Every other example passed; `orders.binz` was the only one.

**The shape of it: a CI step written 2026-09-15 met a language rule written
2026-09-17.** The step's assumption "an example is a program" quietly stopped
being true. Nothing about the compiler was broken — build ok, 125 tests pass.

### Why GitHub let him merge it — two separate things, neither obvious

He asked this next, and the answer was not "the check was red and ignored".

1. **CI never ran on PR #8 at all.** `get_check_runs` -> `total_count: 0`.
   Confirmed `.github/workflows/ci.yml` does not exist at #8's head sha
   `f30ca5c` — that branch was cut from `8d8b04f`, before CI existed.
   The timeline is the whole story:
   - 09-17 21:26 — #8 opened (main had no `ci.yml` yet)
   - 09-18 **19:57:21** — #7 `chore: adding ci` merged, `ci.yml` lands on main
   - 09-18 **19:58:20** — #8 merged, **59 seconds later**

   `pull_request` workflows trigger on **opened/synchronize**. At both of those
   moments for #8, `ci.yml` existed nowhere. Merging #7 afterwards does *not*
   retro-trigger runs on open PRs. One-time ordering accident; won't recur, any
   branch cut from main now carries the file.

2. **`main` is `protected: true`, but protection != required status checks.**
   The tell: a required check that never reports *blocks* the merge ("Expected —
   waiting for status to be reported"). #8 merged clean with zero checks, so
   either no required-check rule is configured or he bypassed as admin. I could
   not read branch-protection settings with the GitHub tools available, and said
   so rather than guessing. Told him where to look and to also tick **Require
   branches to be up to date** — without it, a PR off a stale main can pass its
   own CI and still break main, a slower version of exactly this.

**Also: main has never had a completed green run.** #7's merge triggered a push
run on main, #8's merge triggered another 59s later, and `concurrency:
cancel-in-progress` on `ci-refs/heads/main` almost certainly cancelled the
first. Main's first *finished* run is the failing one. Nothing to roll back to.

**Flagged, unresolved:** the only green run ever — `build & test` on #7 —
reports started 18:26:18 -> completed 18:26:25. **Seven seconds**, which cannot
cover checkout + toolchain + `cargo build --all-targets` + `cargo test` +
seven examples. I cannot read Actions logs through MCP (no workflow tools), so
I did not assert it was wrong, only that it is worth opening. Could be
unreliable check-run timestamps. **Still unverified by him.**

### The fix

I gave him three options and recommended the first; he took it ("fix the run
the examples things").

1. **Skip files without `main` in the run loop** — keeps `orders.binz` honest as
   the file that demonstrates "no `main` required", costs one line.
2. Give `orders.binz` a `main` — undoes yesterday's decision, re-implies a test
   file needs a program.
3. Split `examples/` and `examples/suites/` — reintroduces the `tests/`-shaped
   folder he rejected yesterday.

Two steps now, split by *what the file is*:

- **Run the examples** — `grep -q '^function main'` guards the `binz run`, and
  the else-branch **echoes `skip ... (no main, test-only)`**, so a `main` that
  goes missing by accident cannot hide in a silent skip.
- **Test the examples** — `binz test` over *every* example. Not redundant:
  `binz test` compiles the file and its whole import graph, so it covers the
  files the run step skips, **and it is the only CI step that type checks a test
  at all** — `binz build`/`binz run` never compile one. That partly closes the
  "a test is not type checked" gap flagged 2026-09-17.

`binz test` exits 0 and prints "no `@test` functions here" on a file with no
tests, so the second loop is safe over all seven. `examples/modules/rates.binz`
needs no separate entry — the glob skips the directory, and `binz test
orders.binz` pulls it in through the import graph anyway.

### Verifying it, including that green wasn't vacuous

Ran both loops under `bash -e` exactly as Actions does: run-step exit 0 (six
run, `orders.binz` skipped), test-step exit 0 (5 tests pass in `orders.binz`).

Then the part worth keeping: **a canary**. Dropped in a temp
`examples/zzcanary.binz` with no `main` and a deliberately failing
`test.equal(1, 2)`, and confirmed **run-step exit 0 (skipped) but test-step
exit 1 (caught)**. That is the proof the `grep` skip does not open a blind
spot — without it, "both steps green" could just mean the skip swallowed
everything. Removed the canary; tree clean but for `ci.yml`.

Left uncommitted, as always — commits are his.
