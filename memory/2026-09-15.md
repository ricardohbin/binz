## Session 1 — local modules: `import @root/<path>.binz`

He opened with the syntax already in hand: "let's create local imports based
in tomorrow import sintax. I am thing about support relative paths based in
root project: `import @root/..../some-module.binz`. this module will export
every function on it, for now."

Branch was already `feat/import-local`, clean, on `main` at `c227cd5 feat:
create module map and add sorted map data structure (#5)`. This closes the
first thing I flagged on 2026-09-14 ("no user modules — that is the obvious
next thing and I did not guess at its syntax"), and it is the first time the
`binz/` prefix pays for itself: `binz/...` and `@root/...` are now two
namespaces that have to be told apart.

### The design, and the one-way argument for each piece

- **`@root` is the directory of the file handed to `binz`.** binZ has no
  manifest, so there is nothing else it could honestly mean. The point of
  anchoring at all is that a path means the same thing wherever it is
  written: no `../`, no path relative to the importing file, no way to reach
  outside the root. One file, one spelling.
- **The binding is the file's own name, always** — `geometry.binz` binds
  `geometry`. This is not a new rule, it is the existing one: the last
  segment of `binz/io` binds `io`. No `as`, no wildcard, no bare import,
  same as the stdlib.
- **So a module file is named with one lowercase word**, checked in the
  parser. The name is not decoration, it is the identifier the importing file
  will type, and binZ spells a module lowercase (settled 2026-09-14). That
  makes **his own example, `some-module.binz`, an error** — flagged to him,
  and the diagnostic explains the reason rather than complaining about a
  stray `-`. Directory segments are held to the same rule; one convention,
  checked where the path is written.
- **`.binz` is required.** `@root` already distinguishes a local import from
  `binz/`, so the extension is redundant for the *parser* — but it is what he
  wrote, and requiring it makes the import name a file the reader can open.
  Writing `@root/math;` names the fix.
- **A module exports every function it defines, and nothing else.** His
  "for now", and it needs no keyword: no `export`, no `pub`, so a module's
  surface is exactly what you can read at the top of it.
- **Structs stay inside the file that declares them**, including in the
  signature of an exported function. That is not a restriction I invented —
  struct ids are per file, so the importing file has no way to *write* the
  type. Refused at the call site with the reason, so a module can still use
  structs internally and export everything else.
- **A module imports what it uses.** The file that imports it is not a scope,
  so a module calling `io.print` writes `import binz/io;` itself. Falls out
  of making imports per file, and it means a module can be read on its own.
- **A module does not define `main`.** `main` is the program; a module is a
  library. A module that grew one is almost certainly a file meant to be run.
- **A local module may not take a stdlib module's name.** `io.print` means
  one thing everywhere or the qualification buys nothing.
- **Names are per file.** Two files may both define `add`; neither shadows
  the other. This is the same argument that made mandatory qualification
  worth it on 2026-09-14 — two modules may both define `find` and there is
  no resolution rule to learn.
- **A module function is an ordinary value**, by the rule from 2026-09-14: a
  function is a value exactly when its type is writable in binZ. A user
  function's always is, so `const f: function(i32): i32 = geometry.square;`
  works and needed no new code.

### Implementation

New `src/loader.rs`: entry file -> the graph of files it imports. DFS,
dedup by canonicalized path (a file reached twice through the graph is
compiled once), cycle detection against the open stack with the whole chain
in the message. `@root` is canonicalized once so "cannot read" can say where
it looked.

`CompileError` gained `file: Option<String>` and `at_file`, which only sets
it if unset — the innermost frame that knows the file wins, so a nested
compile is never relabelled by its caller. **A span alone no longer locates
an error**, and that was the single most invasive consequence of the whole
feature.

The compiler's real change is that names became per file. `imports`,
`struct_ids` and `fn_ids` moved into a `FileScope` vec indexed as
`Program::files`, with a `cur` cursor; `structs`, `sigs` and `strings` stay
global because they are what the bytecode holds. `Compiler::run` was five
inline phases over `&[Item]`; it is now five named methods driven by
`each_file`, which sets `cur` and labels every diagnostic with its file.
Every phase runs over every file before the next begins, so a module and the
file importing it are indistinguishable — either may be written first.

`funcs` is now indexed by function id rather than appended to, because ids
are handed out per file and the old code relied on push order matching.

**No bytecode change at all**: functions from every file land in one table,
`entry` is still an index into it, artifact `VERSION` stays 3. That is worth
keeping in mind — the VM never learns that modules exist.

`module_base` answers a new `ModRef` (`Std(name)` / `Local(file index)`)
instead of a `String`, and the local arm of a call just pushes the function
and falls into the ordinary `finish_call` path.

84 end-to-end tests green (18 new) plus 7 unit. Tests got `write_project`,
since `@root` needs a real directory. New `examples/modules.binz` +
`examples/modules/{geometry,tally}.binz` — three files, with `tally`
importing `geometry` so the transitive case is in the example and not only
in the tests. README has a `## Local modules` section.

## Session 2 — `as`, and the rule that makes a rename not a second spelling

Straight after: "to avoid two modules with the same name, we can to implement
`as othername`. but this only is allowed when there are two modules with the
same name, BOTH need to 'renamed'" — then immediately, "two or more, for
sure."

**This is his rule, and it is a sharp one.** A plain `as` is exactly what the
one-way rule forbids: it gives a module two spellings, the default binding and
the alias, and you pick. His version removes the choice. `as` is legal only
where the default is *unavailable* — two or more imports in one file whose
files are named the same — and then it is **required on every one of them**,
so a name is never the default for one import and a rename for another. Inside
the clash there is exactly one way to write the import; outside it there is
exactly one way too, and they are different ways because the situations are
different.

The corollaries all fall out, and I took them rather than inventing anything:

- **`as` on a standard library import is always an error.** No two stdlib
  modules are named the same, so the clash can never arise, so the default is
  never unavailable. That is what keeps `io.print` reading identically in
  every file of every program.
- **A rename to the module's own name is an error** — `as math` on
  `math.binz` is not a rename, and allowing it would put the bare spelling
  back in play.
- **A rename may not be a stdlib module's name**, same reason a local file
  may not be.
- **A rename is a module name like any other**: one lowercase word.
- **A clash is per file**, so the same module is `math` in a file importing
  only it and renamed in a file importing both. Two spellings for one file
  across the program, one spelling within any file. Flagged below; I think it
  is the only workable reading, since a whole-program rule would make adding
  an import to one file break another.
- **Two imports of the same file** are a duplicate, not a clash, so
  `contested_names` counts distinct *targets*, not import statements.

### Implementation

`Tok::As`, `ImportDef::alias: Option<Alias>`, and `own_name()` beside
`binding()` — the first time those two differ. `contested_names(f)` runs
before the import loop and returns the names claimed by more than one file,
with the import texts for the diagnostic; `check_rename` is a four-way match
on `(alias, clash)` where two arms are errors, one is the ordinary case and
one is the renamed case. The whole rule is that one match.

`stdlib::join_or` grew a sibling: `join_with(items, conj)` now backs both it
and a new `join_and`, since "`a` or `b` are named `math`" read wrong.

Note the duplicate-import message changed: it now names the *file*
(`@root/math.binz is already imported`) rather than the binding, because with
renames the binding is no longer the interesting part. One existing test
updated.

10 new tests (94 end to end, 7 unit). `examples/modules/` grew a real clash
rather than a contrived one — `text/format.binz` and `number/format.binz`,
which is exactly the situation the feature is for. README has an
`### as, only where it is forced` section and three new rows in the
guiding-rule table.

### Flagged to him, undecided

- **A clash is per file**, so one module can be `math` in one file and
  `geomath` in another. Per-file is the only rule that does not make adding
  an import to one file break another, but it does mean a reader who moves
  between files sees two names for one module.
- **`as` cannot resolve a clash with the standard library.** A file named
  `io.binz` is refused outright rather than being renameable, because
  renaming `binz/io` (which his rule would require of *both*) would be worse.
  So there is one place the rule is not mechanical. His call.

## Session 1, flagged to him, undecided

- **`some-module.binz` — the name he actually typed — is an error.** One
  lowercase word, because the file name is the binding. He has corrected
  naming twice before (2026-09-14), so this is the one most likely to come
  back.

  moves the root. A manifest (`binz.toml` or similar) would pin it properly.
  There isn't one, and I did not invent one.

  two files cannot share a data type — a real limit on how far a program can
  be split. The next thing to decide, probably before anything else here.
- **No `main` in a module, and no per-module entry point**, so a module
  cannot be run on its own to test it.
- **Nothing stops two modules in different directories having the same file
  name**; it is only an error if one file imports both. That seems right, but
  it is the one place the "binding = file name" rule can bite.

  diagnostic prints the *real* path (`examples/modules/geometry.binz`) while
